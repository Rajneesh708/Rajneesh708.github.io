What every website owner deserves to know

What most website projects
leave unaddressed.

This is not a criticism of any developer. It is information that every person who has ever paid for a website has the right to understand. Knowing what is technically possible to leave out of a website project is the first and most important step in knowing what to insist on.

01 · Performance

The page loads slowly. Nobody mentioned it.

Images not compressed. CSS and JavaScript files not minified. No caching headers configured. No lazy loading for content below the fold. The client never asked about page speed, so no one built for it. On mobile – where most traffic now arrives – a slow page loses a visitor before they have read a single word.

02 · Mobile & Accessibility

Designed on a desktop. Tested on a browser resize.

Not on an actual phone. Text overflows. Buttons are too small to tap. Navigation collapses in ways no one anticipated. Images have no alt text. Keyboard users cannot navigate the page. These are not edge cases – they are the default output of a build that was never tested in the environment where most people will use it.

03 · Backend Integrity

Forms that accept anything. Including what they should not.

Input not validated on the server – only in the browser, where validation can be bypassed. Admin panels using credentials that were never changed after the initial setup. Private API keys written into client-side JavaScript, visible to anyone who views the page source. When the server trusts whatever the browser sends, the server can be made to accept anything.

04 · Payment Security

The amount was calculated in the browser. Not on the server.

Payment totals computed only in client-side code, where they can be modified before reaching the payment gateway. Payment confirmation handled by a browser callback rather than verified through the gateway's server-side webhook – which cannot be forged. A site that does not verify payment server-side can be made to confirm a payment that never completed.

05 · Data Protection

User data collected. What happens to it is unclear.

Names, email addresses, phone numbers, and form submissions stored without encryption. No process for a user to request deletion of their data. Third-party tracking scripts embedded without clear disclosure. Backups taken but never tested for restoration. A backup that has never been tested is not a backup – it is a file that has not yet been needed.

06 · Security & Search Visibility

No security headers. No sitemap. Pages undiscovered for months.

HTTPS not enforced across the full domain. No Content Security Policy header, leaving cross-site scripting possible. Third-party packages left unupdated as known vulnerabilities accumulate publicly. Title tags duplicated across pages. No Schema.org structured data. Sitemap never submitted. Canonical tags absent. A website that search engines cannot read is invisible to the people it was built for.

The point is not that developers intend to leave these things undone. It is that most clients do not know to ask for them – and most projects are scoped in a way that does not require them to be included. The responsibility for asking is with the client. We are telling you what to ask for.

The MECULS Standard

What we build and what
we will not move on.

Every website MECULS builds is built to the same standard – regardless of sector, scale, or timeline. The standard is not a premium tier. It is the only tier. Data is either protected or it is not. HTTPS is either enforced or it is not. Input is either validated server-side or it is not. The middle ground is where vulnerabilities live.

We build with complete integrity: no undisclosed shortcuts, no code we cannot explain, no technology choices made for our convenience rather than yours. If something will take more time to do correctly, we say so before we begin – not after we have delivered it.

Zero vulnerabilities at launch

Every form validated server-side. Every API endpoint rate-limited. Every package vetted and current. No known vulnerability left unpatched. Nothing shipped with a door that should be closed.

No technology lock-in

The code we write is yours. The platforms we use are open and fully documented. You can hand the entire codebase to a different developer tomorrow. No proprietary format, no hidden dependency on our continued involvement.

Complete documentation

Every page, every form, every integration, every API call is documented. If something needs to be fixed in two years, the next developer does not need to reverse-engineer what was built. The documentation tells them.

Data protection by design

Encryption at rest. HTTPS enforced across the full domain. Data deletion mechanisms in place before the first user submits anything. No third-party tracking without your explicit knowledge and consent.

Technology

What we use
and why.

Technology choices are made on three criteria: secure by design, cost-effective without hidden ongoing fees, and open enough that you are never locked into a single vendor. We do not recommend a technology because it is fashionable or because it generates recurring revenue for us. We recommend it because it is the right fit for the specific requirement in front of us.

What we use
  • GitHub Pages – zero-cost, high-reliability static site hosting. No server to maintain, no monthly hosting invoice, no single point of failure.
  • Supabase – open-source database, authentication, and API platform with row-level security. Your data is in a standard PostgreSQL database. You can export it in full at any time.
  • Cloudflare – CDN, DDoS mitigation, and Web Application Firewall at the network edge, before a malicious request reaches your application. Free tier covers most requirements.
  • Modern HTML, CSS, and JavaScript – browser-native, platform-independent. No licence fees, no plugin ecosystem to maintain, no framework dependency that becomes a liability after the project closes.
  • Cloudflare Turnstile – bot and spam protection without user friction. Privacy-respecting. No CAPTCHA puzzles for genuine visitors.
  • Razorpay / PayPal – Indian and international payment integration, with server-side payment verification through the gateway's signed webhook. Payment status confirmed by the gateway – not by the browser.
What we do not use, and why
  • Plugin-dependent CMS platforms – platforms that rely on a large ecosystem of third-party plugins introduce maintenance overhead, recurring plugin fees, and security exposure that grows with each additional plugin. For most business websites, a well-built static or database-backed site achieves the same result with none of the ongoing risk.
  • Proprietary visual page builders – drag-and-drop tools that generate bloated, inaccessible markup that performs poorly on search engines and cannot be cleanly maintained by a developer who did not build it inside the same tool.
  • Undocumented SaaS backends – platforms where your data is stored in a proprietary format with no standard export path. Migration, should you need it, becomes expensive or structurally impossible without starting over from the beginning.
Scope

The kinds of websites
we build.

Scope is determined by what the business requires – not by what is easiest to deliver. Each of the following is a distinct technical undertaking with its own architecture, security model, and data handling requirements.

01

Static Informational Sites

Multi-page brand and information websites. Fast, inherently secure, zero ongoing hosting cost on GitHub Pages. Every page properly indexed: Schema.org structured data, correct canonical tags, unique title and meta per page, sitemap submitted at launch. Ideal for service businesses, professional practices, and organisations with stable content.

02

Dynamic Data-Driven Sites

Sites that read and write to a database: directories, booking portals, member areas, dashboards, and content portals. Built on Supabase with row-level security, proper server-side authentication, and validated data handling – not a frontend login screen placed over an unprotected database.

03

Payment-Integrated Sites

E-commerce, course enrolment, event registration, and service booking with integrated payment processing. Every payment amount verified server-side through the gateway's signed webhook. No client-side manipulation possible between the visitor's browser and your account.

04

Registration & Form Portals

Complex multi-field forms for enquiry, registration, application, and data collection. Full server-side input validation, rate limiting on submission endpoints, spam protection, and structured data storage. What reaches the database is exactly what the user submitted – not what someone injected.

05

Corporate & Enterprise Sites

Multi-division sites with structured navigation, extensive content, and multiple stakeholder audiences. Full SEO architecture from the first page: Schema.org per page type, sitemap submitted at launch, canonical tags correct, no duplicate content, no pages accidentally blocked by a wrong robots.txt entry.

06

Audit & Rebuild Projects

Existing website review, vulnerability assessment, and targeted or full rebuild. We identify what the original build left unaddressed – across performance, security, data protection, accessibility, and search visibility – and correct it without dismantling what is already working correctly.
